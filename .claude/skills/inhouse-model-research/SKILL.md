# 自研模型研究：对齐并超越 S家

这个 skill 不是一套固定流程。它给你三样东西：目标到底是什么、怎么可靠地量、以及前人走到了哪里。具体怎么突破由你判断。好的结果往往来自换一个问题的提法，而不是把阈值再调一遍。

## 目标

产品要求（用户，2026-10-29）：
- 机位手机上实时出结果；
- 球场自动识别；
- 正式版只用自研；内测阶段自研和 S家并存，可以对比；
- 只用自研代码、自训练模型和可商用的开源模型，因为 App 要上架售卖。

**研究范围**（用户，2026-11-04）：只围绕三项核心功能，即两端的发球识别与发球球速、近端界内外（发球和对拉，覆盖率的瓶颈是触地召回）、录像与导出。对拉动作类别、对拉球速、远端界内外保留现状，不再作为研究目标；改动不能让它们变差，但不为它们单开一轮。

**达标线**（用户，2026-11-11）：以前写的「三项过 80%」只是短期合格线。目标是发球识别、发球球速、近端界内外三项都到 90% 以上，再往上超越。报告时两种口径都要写：判出来的有多准，以及按参照行算的端到端比例（分母是参照里所有该判的拍，没判出、没给球速的都算没做到）。只报前一种会把「少判」当成进步。

"对齐"是指在同一段视频上，自研给出的击球、动作和球速与 S家 接近。"超越"是指对照独立参考时比 S家 更准、覆盖更多，并且仍然在 iPhone 上实时。

有一点要看清：S家 本身不是真值。离它越近，"和 S家 的一致率"就越没法说明谁更好。要宣称超越，需要独立参考：第二机位、物理一致性检验，或我们自己的离线老师（更慢、更准、能和物理互相核对）。不用雷达（用户 2026-11-03 决定、2026-11-05 确认）。这些参考都要自动产生，不靠人工标注（见下文"真正的边界"）。所以在追赶 S家 的同时，也要为"超越"那一天准备这些参考。缺什么参考，就把"怎么自动得到它"当作研究任务的一部分。

## 三类模型

- **S家 App**（参照 App 的桌面版，装在你自己的 Mac 上）：只当参照。它导出的逐拍结果就是参照行（"老师行"），test.MOV 有 96 行，double-test-003 有 127 行。App 会更新，引用时写明当天用的版本。
  - 怎么拿参照行：在自己的 Mac 上装 S家 App，用它分析同一段视频，导出逐拍结果（击球时刻、动作、球速），整理成 `compare_rows.py` / `serve_score.py` 能读的老师行：`[{"anchor": 秒, "speed": km/h, "stroke": "正手"}, …]` 或 `{"teacher": [...]}`。导出的时间和视频时间差一个固定偏移（double-test-003 上锚点 = 导出时间 + 2.0 秒），先用几拍明显的发球核对一下。打分时加 `--tolerance 0.6`（见 `references/landscape.md` 第 5 节）。
  - S家相关的笔记只保存在本地，见 `docs/s-reference.local.md`（可选，不在 Git 里；没有这个文件也不影响开发，上面的导出流程就够用）。
- **App 里的 S家链**（本项目在 App 里运行的 S家模型）：内测对比用，也能用 `court-analyze` 给任何视频生成参照行。模型不在 Git 里，要开发者自己把 S家模型放到 `.local/s-models/`，再用 `COURT_MODEL_SET=both` 或 `sjia` 构建（`scripts/prepare-analysis-models.sh` 会校验并暂存到 `.local/AnalysisModels`）；默认构建只带自研，没有 S家链。没有这些模型时，用 S家 App 的导出行当参照即可。它的输出和 S家 App 不同：test.MOV 上动作几乎一致（87/88），球速约低 9%。引用时说清是哪一个。
- **自训练**：用自己的视频和自动生成的标签训练或微调的模型，进展见 `docs/speed-model-training.md`。权重和训练数据都要能商用。
- **自研**：`Sources/CourtCore/IndependentAnalysis/` 下的 Swift 规则、几何、实时链和自动球场标定，加上开源模型（TrackNetV3 MIT 权重，Apple Vision）。

## 怎么量

一轮实验的骨架：
1. 用一句话写下假设：改什么，为什么会更好。
2. 在当前 main 上用同一条命令跑基线。
3. 做改动。
4. 用同一套工具在开发视频和留出视频上都跑一遍，同时记下耗时。
5. 记下结果，包括没用的结果，再决定下一步。

工具（详细命令见 `references/landscape.md`）：
- **自研实时链**：`court-analyze independent-live VIDEO MODEL_DIR auto OUT.json`，和 App 机位走同一条链（NV12、自动球场、姿态补框）。
- **S家参照行**：`court-analyze VIDEO .local/AnalysisModels OUT.json`（需要本地的 S家模型，见上文）；没有的话用 S家 App 的导出行。
- **打分**：`python3 .claude/skills/inhouse-model-research/scripts/compare_rows.py REF.json RUN.json [RUN2.json …] [--window 起 止] [--json]`。它按击球时刻一对一配对，给出：
  - 检出率和多报的行数；
  - 动作类别的一致率和混淆表，以及"一律答多数类"能拿到的一致率（规则不比它高，就是没有信息量）；
  - 球速的覆盖率、平均误差和中位比。

  它能读 App 的逐拍 JSON（S家行和自研行都是这种格式），也能读 S家 App 的老师行。
- **发球打分**：`python3 .claude/skills/inhouse-model-research/scripts/serve_score.py REF.json RUN.json`，给出发球的精确率、召回、F1 和有速发球的覆盖、离散度。跨链的发球时刻最多差约 0.7 秒，所以默认用 1.0 秒窗口。
- **耗时**：Mac 上每帧缩放、每批推理、每次人员检测的毫秒数都在 `independent-live` 的报告里。iPhone 要用 Phase 0（`COURT_PHASE0=1 COURT_PHASE0_BACKEND=independent`，见 `docs/camera-side-analysis.md` 第 11 节），而且手机运行要短。

这些坑踩过：
- 两条实时链同时跑会互相抢资源，耗时只能在单独运行时量。
- 分析器只保留最近 600 行，命令行报告现在保留全部。看到行数整整停在 600，就去查是不是又被截断了。
- 15 分钟的视频在 M4 Pro 上大约要跑 5 分钟，放到后台去跑，不要干等。

## 开发视频和留出视频

调参时看过结果的视频，都算开发视频，在它上面的提升不能当作泛化的证据。留出视频要求换球场或换机位，只换一个文件不算：1080 和 full_match_video 是同一块场地、同一个机位，2026-10-29 那轮把 full_match 当留出视频，结论因此偏乐观。

当前分组见 `references/landscape.md`。在留出视频上调过参数后，把它挪到开发组并说明原因。留出视频不够用时，去找新素材，比如用户这台电脑上的其他打球视频或新录的视频，并把找新素材当作工作的一部分。

## 往哪里突破

`references/frontier.md` 是一张地图，不是任务单。它按影响排列了已知差距和背后的证据，记录了试过什么、结果如何，也列了还没试的想法。用它少走弯路，但不要被它限制：
- 规则调到头的地方，考虑换学习方法；学习方法缺数据的地方，考虑用物理当免费的监督信号。
- 质疑结构本身。比如球速覆盖率低，问题可能在球检测，不在拟合。
- 离线可以用慢而准的方法，再把它的结果当老师，蒸馏给实时模型。这个老师是我们自己的，不涉及 S家 的输出。
- 能用小实验先证伪的想法，就先做小实验。

每轮结束，把学到的东西写回 `frontier.md`，包括证伪的想法和它为什么失败。下一个智能体从那里接着走。这份文件越准，这件事推进得越快。

## 真正的边界，以及原因

这类约束很少，但都是硬的：
- **可商用**：发布或用来训练的模型、权重、数据和代码都要允许商用，来源和许可写进清单与 `Sources/CourtCore/Notices/`。S家 的权重和输出只做参照，不做训练标签，也不进产品。Apple Vision 的输出能不能当训练标签还不明确（设计文档第 6 节），用到时要明说。
- **实时**：采集回调里只做常数时间的工作，分析不持有相机缓冲，积压时重置而不是拼接轨迹。实测机型目前只有 iPhone18,2。新的计算先在 Mac 上估算成本，再用 Phase 0 实测。
- **产品不变量**（`AGENTS.md`）：
  - 未知保持为空，不按 0 计；
  - 球速和落点是模型估计，不叫测量；
  - 采集固定 1920×1080、60 fps；
  - 不做计分。
- **不做人工标注**（用户，2026-10-30）：整个开发和训练流程里都没有人工标注这一步，太耗神。不要计划人工标注，也不要问谁来标注。训练标签和评估参考都要自动产生，例如：
  - 物理当监督：拟合残差很小的飞行段里的球点当伪标签，触地、过网的几何当一致性检查；
  - 我们自己的离线老师（高分辨率、多次推理、更大的模型、双向时间）蒸馏给实时模型；
  - 多帧、多模型、正反向一致才收的标签，以及照着已知物理合成或渲染的数据；
  - 练习安排本身当参考（一段只打一种动作），以及量好坐标的标记这类实测读数；
  - 录像有声音时，用击球和触地声定时间。
  智能体看画面判读也不算真值：10-30 那轮在 55 px 的远端人上分辨不出正反手。
- **隐私**：用户的视频、帧、中位图只能放在 `.local/` 或临时目录，不进 Git，不进截图。
- **证据**：
  - 和 S家 接近不等于准；
  - 开发视频上的结果不能算泛化；
  - 跳过的检查不算通过；
  - 报告写清跑了什么。

## 交付一轮研究

- 一张对照表：基线和新版，分开发视频和留出视频，用同一套工具；再加耗时、没用的尝试和下一步假设。
- 更新 `docs/model-replacement-design.md` 里的状态和表格，在 `docs/verification.md` 追加一节带日期的记录，再更新本 skill 的 `references/frontier.md`。
- 代码按仓库约定走 PR（见 `AGENTS.md`）。新模型走固定清单流程（`scripts/prepare-independent-ball-model.py`、manifest、许可说明），换模型要同时更新清单和核验结果。
