# 统一 App：以网球分析为核心

2026-10-26 用户明确取消计分，核心为球速、落点和动作分类。此前以人员看板和手动比分为中心的方案不再采用。

## 两种角色

同一原生 SwiftUI App 运行于 Mac / iPhone，每次选择本机角色。2026-10-28 起分析放在机位端（设计与取舍见 [机位端实时分析方案](camera-side-analysis.md)）：

- **机位**：挂在场边的手机。1920×1080 / 60 fps 采集，录像与实时分析都在本机完成，会话、录像和逐拍结果的权威副本保存在机位上。没有看板时也能单独开始、暂停、结束记录并在历史里回看。支持 iPhone 13 及更新机型（型号代号 iPhone14,x 起，含 iPhone SE 第 3 代），其中只有 iPhone 17 Pro Max（iPhone18,2）做过负载实测，其他机型在机位页提示未实测；Mac、模拟器与更早的 iPhone 进入机位角色可以配对和看历史，但「开始采集」会明确拒绝。
- **看板**：Mac 或另一台 iPhone。显示二维码，机位扫码后主动连接；通过协议 v2 收到逐拍数据、1 Hz 机位状态和按需的低清预览（640×360），保存会话镜像，并把开始/暂停/继续/结束、标记、持拍手、四角标定（机位发一张全分辨率静帧）和「唤醒机位屏幕」发给机位执行。记录中可以向机位要某一拍前后几秒的片段（Phase 3），会话结束后可把整段录像回传到看板。

- **浏览器看板**（2026-10-28，设计见 [web-display.md](web-display.md)）：安卓、平板或任何电脑的浏览器。连接方向与 App 看板相反：机位在本机开 HTTP + WebSocket 服务（2026-10-29 起默认开启，是主推的连接方式：机位侧栏顶部「连接」打开全屏连接页，先问对方是否装了 App，再只显示对应方向：浏览器扫机位的码，或机位扫 App 看板的码），浏览器扫码或输入地址与 6 位配对码连过来；同一 Wi-Fi 或机位个人热点，不支持点对点直连。复用协议 v2 的 JSON 消息，可多台同时连接、都能控制（回执只回发起者，冲突以机位为准）。浏览器是瘦客户端：历史、片段（`.mp4`）和录像下载都从机位实时读取，不存镜像；预览是分析器最新帧的 640×360 JPEG（最多 5 帧/秒，L1 每秒 1 帧，L2 起停发）。走明文 HTTP，弱于 App 看板的 TLS-PSK。

网络只影响看板的显示延迟，不影响分析：断线时机位继续录像和分析，重连后把完整逐拍清单补发给看板。两台设备可以在同一 Wi-Fi 或个人热点下连接；看板开启「允许点对点直连」（默认开启）时，也可以不在任何网络、只打开 Wi-Fi 直接连接（Phase 3，待实机验收）。暂为单路视频，无云账号、远程观众同步或自动计分。

看板的首要信息为每拍球速估计、球场落点候选、动作类别；人员检测与机位状态（电量、温度、降载级别、分析落后、数据速率）放入辅助区。手机横屏左右独立滚动，竖屏单列；辅助大字号优先阅读和触达。

## 分析链路

1. 机位采集帧在采集队列上只做常数时间工作：选帧器给每帧一个时间刻度，只把引擎需要像素的帧（60 fps 时每 6 帧中的第 0、1、2 帧）复制进分析自有的缓冲池，绝不持有相机缓冲；录像时同一帧送 8 Mbps 编码；看板请求预览时每 4 帧取 1 帧在独立队列缩放编码。分析积压或缓冲池满时明确重置时序状态，不跨缺口拼接轨迹。
2. S家链（对照用，代码和模型都只在本地，见 [s-reference.md](s-reference.md)；上架版和默认构建里没有）：通过 `ReferenceChain` 接入机位分析器，消费机位的原始采集帧，按 `TennisFrameCadence` 调度视频帧对。
3. 动作目前覆盖落地击球、截击、发球、高压、喂球和未知。未确认持拍手与击球者关系时不把左右翼直接写成正手/反手。测速牌的「发球」模式只统计判为发球且有有效球速的拍次（`TennisServeSummary`）。
4. 球速输出是模型估计，未由雷达/物理真值验证。地面单应性不用于空中球测速。
5. 触地事件在独立的低优先级队列（最多 1 个任务在跑）另跑重叠网格中的触地热图定位和球场裁剪模型，结果按稳定 ID 回填，不挤占主节奏；只接受高分且无竞争的图像位置。不能把粗事件模型的图像位置头当逐帧网球检测。定位用相邻源帧，与粗网络帧对节奏分开。
6. 自动球场映射需要足够可见语义地标、独立点验证和几何共识；落点候选还需要其实际相邻两帧映射一致。失败时显示原因，不伪造坐标。
7. 球场只靠自动识别，没有手动标定（2026-11-04 去掉）。识别不了时显示原因，落点与界内外保持未知。只映射支持凸包内的点，范围外保留未知。换流自动失效；机位改镜头倍率时重启时序分析并重新识别球场（倍率只在开始记录前或暂停时可调，见 camera-side-analysis.md 第 6 节）。
8. 每拍先以稳定ID发布动作候选，再随后续画面补充球速/落点，记录按ID更新而非重复计数。主UI展示近期候选，完整会话保存逐拍结果、模型版本和标定状态。

当前是有界滚动分析：动作较早出现，球速通常等待触地。机位发热时分级降载（只削减预览、人员检测、触地定位和分析，不降帧、不降分辨率）；L3 暂停分析期间录像继续，会话记录分析暂停区间，可在录像上离线补算。录像不等待分析，但不能声称所有设备都达到固定毫秒延迟。长时间温升、耗电与精度仍待实机/标注验收。

## 模型与来源

默认构建（`COURT_MODEL_SET=independent`）只带自研模型。S家链的模型不在 Git 里：开发者自己把 S家模型放到 `.local/s-models/`，`scripts/prepare-analysis-models.sh` 按固定 manifest 逐文件校验后暂存到忽略目录，只有 `COURT_MODEL_SET=both` 或 `sjia` 的构建才打包，运行时不下载。不宣称完整复刻 S家 App。（S家相关的笔记只保存在本地，见 docs/s-reference.local.md；没有这个文件也不影响开发。）

S家链没有移植 S家 App 原版的全部处理，例如离线细化、身份与持拍手、自动计分和模型直接给出的界内外分类。本项目不把随机补全坐标当检测事实。

### 导入视频（2026-11-04，1.1）

不在球场的人（包括 App 审核）也能试分析：启动页「导入视频分析」从「相册」（系统照片选择器，不需要相册读取权限）或「文件」选一段视频，App 用机位同一条链分析，结果存成历史里的一条普通记录（`capturedOn` 为「导入的视频（非实时机位）」，标题「导入 · 文件名」），逐拍回看、筛选、片段与存到相册照常可用。

- **同一条链**：`VideoImportRun`（CourtCore）建一个不配对、不开浏览器服务的 `CameraSessionController`，配机位自己的 `CameraMediaPipeline` 和自研实时链（`CameraSideAnalyzer(independent: .bundled())`，打包的 FP16 模型），由 `FileFrameSource` 把视频逐帧送进去。只用自研模型，任何构建里都不加载 S家权重；没有自研模型的构建（code-only、`sjia`）在页面上说明不能分析。
- **不按墙钟送帧**：导入时 `FileFrameSource.isReady` 让文件等分析（分析队列少于 16 帧才送下一帧），所以不会因为设备慢而丢帧，结果与设备快慢无关；耗时取决于设备（Mac 上 40 秒视频约 30 秒，模拟器要几分钟；iPhone 上尚未实测，机位能实时分析，预计接近视频长度）。降载策略不生效（`appliesLoadPolicy = false`），分析变慢只会让导入变慢。
- **能导入什么**：自研实时链按 1/60 秒计帧、自动球场识别只吃 1920×1080，所以要求约 60 帧/秒（59–61）、横屏 16:9、至少 720p，3 秒到 10 分钟；画面一律缩放到 1920×1080 再送入。竖屏、非 16:9、太小、30 帧或慢动作（高帧率）、太短太长都在选完后直接拒绝并说明原因（`VideoImport.check`）。机位实时采集不受影响，仍然只有 1080p60。
- **录像**：流水线把画面重新编码成这条记录的录像（与机位相同的 8 Mbps H.264），选中的原文件不复制、不保留；从相册选时系统先给一份临时拷贝，用完删除。
- **生命周期**：分析中显示进度和已识别拍数，可以取消；取消、失败或 App 退到后台都会停下并删除未完成的记录和录像（模型推理不能在后台跑），分析中屏幕不自动锁定。完成后刷新历史，可直接「查看记录」。
- Mac 上的同一流程：`COURT_PROBE_INDEPENDENT=… swift run court-probe import VIDEO SESSIONS_DIR`。

### 存储与导出（2026-11-03）

播放器可以分享或存到相册某一拍（本机录像就地剪出，不重新编码）。历史记录的「管理存储空间」按类别显示占用，可以只删录像、保留逐拍数据（记在 `cleared-recordings.json`，会话 JSON 不变），清理片段、日志与残留文件，并可选自动保留 30 或 7 天的录像（默认不自动清理）。剩余空间不够录 30 分钟时机位和看板都会提醒。

### 界内外（2026-11-03）

看板开启界内外时先选单打或双打，默认只判近端半场。机位按落点到线的距离和落点误差范围判出界、界内或压线附近，结果作为可选字段 `bounce.hawkEye` 随逐拍数据发给 App 和浏览器看板；看板弹卡片，明确出界时喊「Out!」。S家链的落点允许外推到场外的缓冲区，否则出界球没有坐标。规则、误差依据与协议见 [界内外](hawk-eye.md)。全屏测速牌的「界内外回放」按正式比赛的节奏回放判过的拍（标题、轨迹、镜头在落点旁停稳、升到正上方用标尺量出球印到线的距离并画出误差范围、结论），再接机位剪出的单拍视频；轨迹是按击球点和落点估算的弧线。

### 挑战（2026-11-04）

任何一块屏幕（App 看板顶栏与测速牌、机位记录页、浏览器状态栏与测速牌）都能点「挑战」：机位挑最近一个有落点的拍（3 秒内又有新击球就等它的落点），按单打或双打两个半场都判，结果写在这一拍的可选字段 `challenge` 上并随会话保存；所有屏幕第一次看到这个挑战就自动播放回放，并在结论处报「Out!」或「In.」。不需要先开界内外，不限次数。见 [界内外](hawk-eye.md) 第 7 节。

### S家 / 自研切换（2026-10-29）

`COURT_MODEL_SET` 选择打包哪几套模型：默认 `independent` 只带自研；`both` 同时带 S家与自研（S家模型要开发者本地提供，见「模型与来源」），启动页可切换，这种构建里默认 S家，选择按设备保存；`sjia` 只带 S家（旧名 `swing` 仍可用）。选自研时 `AnalysisModelLocator` 返回空：实时分析和 S家离线补算都关闭，不加载 S家权重；机位改用自研实时链（`IndependentLiveEngine`：FP16 TrackNetV3、Vision 人框、v14 规则的滑动窗口版；v14 只改了发球识别），并用 `IndependentLiveCourt` 从画面白线自动识别球场（找到后在单帧上持续跟踪慢慢偏移的机位；被碰或拿起时丢掉旧球场、不补算这段球点，边晃边逐帧重新识别）、记录中定时复查；没有手动四角。内测用 `both` 对比两条链，正式发布只用 `independent` 构建。每个 S家模型的去向、自研替代与阶段计划见 [模型替换设计](model-replacement-design.md)。

### 独立测速开发链（2026-10-29）

`Sources/CourtCore/IndependentAnalysis/` 已提供共享的 owned-RGB8 预处理、显式 Core ML 模型包装、图像候选和过去帧关联，支持 Mac/iOS 的 Swift 接口。`court-analyze independent-frames` 以显式帧包、暂存模型目录运行该链，保留整数 PTS、候选空值和速度不可用原因。它不解码视频、不占相机采集缓冲，也尚未接入 `CameraSideAnalyzer` 的机位节奏；背景是声明包含未来帧的离线输入，不能称实时采集链。

随后新增的 `IndependentVideoReader` 与 `IndependentBallWindowAssembler` 支持 `court-analyze independent-video`：AVFoundation 原视频解码为自有 RGB，明确拒绝非 identity 方向；按原始有理 PTS 筛选，避免范围裁剪改写首帧时间。读取晚段时需从轨道起点顺序解码，不能视为高效随机访问。前48张连续帧先缩放后求中位数形成冻结背景，后续每8张真实帧组成一批，不补齐尾帧；断层/换源/ROI变化清空背景及批次。背景只用过去帧，八帧网络仍有最多7帧等待。此策略与旧的全窗口离线背景不同，已单独验证并报告开发集退化，未据此替换 App 后端。

`ball-camera-calibrate.py` 另提供有来源绑定的条件标定诊断：地面地标求H，再由至少两个明确XYZ的离面点恢复一般K/R/t；原始畸变未知和尺寸假设不会自动升级为事实。`ball-camera-perturb.py` 对冻结声明的点位及共享高度误差做有界敏感性检查，保留失败和全部样本，不选择相机，也不产生置信区间。候选保留帧/变换/半开PTS区间和误差来源，顶层有效相机及速度始终为空；完整标定资格、飞行与机位链仍未完成。用标准网高代替现场测量可能产生低残差但错误速度，实际条件试算及边界见 [几何文档](independent-speed-geometry.md)。

开源基础跟踪模型的 MIT 许可及固定清单在 `assets/independent-models/tracknetv3-base-v1/`，约45MB模型包现位于 `assets/independent-model-weights/tracknetv3-base-v1/TrackNetV3Base.mlpackage`，二进制走Git LFS。Pillow RGB 缩放适配的完整 MIT-CMU 通知作为 `CourtCore` 资源打包。原生同 RGB 预处理已与冻结参考比较，但 ImageIO/Pillow JPEG 解码存在可测差异；该差异及视频/相机色彩、方向、内参和触球分段仍需处理。

扩充开发实验已完成 Gaussian 与官方 binary disk 目标编码两项各 1024 步全网络训练，两项冻结开发门均失败。disk 的来源开发集命中为 81/246，低于官方 base 的 162/246；慢球由 32/32 降至 0/32。失败权重及报告保留，均不转换或激活到 App。完成训练只证明实验执行完毕，不构成模型、球速或原生完整链验收。

独立几何链另有 `IndependentBallisticDiagnostic` 共享 Swift 值类型与 `court-analyze independent-flight PROTOCOL_JSON NEW_OUTPUT_DIRECTORY`。它接收同源原图像素、有理 PTS、显式固定的 row-major K/R/t 假设相机与触地时间，仅求五个运动参数；不拟合相机、不推理新模型、不插补缺点。旧自由相机条件解对两组输入的首观测模长为 10.2443 与 37.7198 m/s，说明条件敏感；另用独立于球点的 FIT8 地面点、方形像素/居中主点/零畸变先验求得相机，2 个可见留出点通过工程界后固定相机，得到 manual41 7.7190067、native40 7.2196152 m/s 的原始条件值。相机与触地等假设未获物理认证，数值接近不代表准确性。

该命令的已接受相机、速度向量与球速字段始终为 null，物理、人审、正式、生产及 20% 验收资格始终 false；原始代数参数仅供开发审查。两组真实输入与 Python 对照均为 6 次 GN，首观测模长差≤4.45e-15 m/s；当轮12项定向测试全通过。

`IndependentBallisticIntervalDiagnostic.evaluate(input:request:)` 现自行拟合一次输入并返回同源 `(fit, rawInterval)`，调用方不能把另一来源的 fit 配给本输入。`independent-flight` 沿用 v1 schema，可选 `interval` 字段；未提供时保留旧行为。新增输出为明确时间区间上速度模长的积分均值及起末速度，区别于原 `rawMotion` 的首观测模长。区间严格满足 `start < end <= contactTime`，触地端点取碰撞前左极限；超出全部原非缺失观测包络（包括最后观察至触地）须给显式外推原因，不能跨已知碰撞或裁剪坏观测来修复原拟合。原 fit 状态/原因与失败质量均保留，积分成功不会提升 accepted 字段。

## 生命周期与存储

- 未开始记录也可在机位上实时分析（看板显示会话外的最近记录）；开始后才把该段逐拍事实归入会话并录像。
- 会话归机位所有：看板开始的会话由机位采用同一 ID；两端各有进行中的会话时以机位为准，看板本地会话结束并保存。看板的操作是请求，机位执行后回发会话副本；机位不在线时看板先在本地生效并排队，重连后重放。
- 暂停结束本段录像，并让分析器处理完已准入的帧、结束未完成的拍次、等待触地定位队列后封存；继续开启新的分析时序段和录像片段；结束保存稳定 ID 的逐拍结果及来源时间，历史可定位对应视频。
- **断流不暂停**；机位的相机被系统中断、方向改变、退到后台或停止采集时暂停。看板退到后台时，只有没有机位加入的看板本地会话才暂停。来源流变化、时间断层、丢帧或分析积压都会重置时序状态，不跨段拟合运动。
- 录像保存在机位，看板的镜像标注「录像保存在机位设备上」；结束后可在看板历史中「传到本机」（断点续传、SHA-256 校验，机位记录中不允许回传）。
- 单拍片段（Phase 3）：看板的击球列表与历史可「从机位取这一拍片段」，机位不重新编码，剪出击球前 2 秒到触地后 1.5 秒（最长 10 秒），记录中也能取；正在录的这一段只在内存里保留最近 30 秒，更早的拍次在暂停或结束后从录像里剪。片段以小块发送，不挤占实时数据；看板存为 `Clips/<会话ID>/clip-<拍次ID>.mov`。
- 机位录像中、标定可用且无操作时自动进入省电值守：不挂载预览层、纯黑并调暗屏幕，轻点唤醒 15 秒；看板可远程唤醒。
- 旧版历史仍可解码，其手动比分事件只保留为旧记录，不参与新的分析统计。没有网球分析的旧会话显示未采集分析，不伪造零结果。
- 会话 JSON 保留网球分析与分析暂停区间；辅助人员日志在机位上单独存为 JSONL，MOV 旁保留逐帧来源 PTS 日志。全部留在两台设备本机。
