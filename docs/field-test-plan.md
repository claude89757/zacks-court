# 球场实测方案

一次在真实球场上的验收，用独立参考检查动作分类、球速估计和落点候选，同时验证点对点直连、记录中取片段、实际机位位置，以及（练得够久时）温升与耗电。通用的验收要求见 [实机验收清单](device-validation.md)；结果按日期写进 [验证记录](verification.md)。

App 的球速和落点是**模型估计与候选**。这次测试只给出它们与独立参考的差距，不调参数、不改门槛，也不据此宣称雷达级测速或判罚级的界内外（界内外只是估计）。

**不做人工标注**（用户 2026-10-30）：不逐拍看录像标动作、不补录漏检、不标误检、不凭录像判断落点。参考只来自练习安排本身（一段只打一种动作，段名就是动作参考）和仪器读数（雷达、量好坐标的标记）。

## 暂定门槛（测试前可改，开始后冻结）

验收清单要求在测试前写定门槛，事后不按结果挑样本。下表是暂定值，出发前可以改；一旦开始记录就不再改动，结果无论好坏都如实记下。

| 项目 | 分母 | 暂定门槛 |
| --- | --- | --- |
| 击球检出 | 每段计划的球数（喂球或发球数按安排固定） | App 拍数达到计划数的 ≥ 90%，多出的按误检看 |
| 球速覆盖 | 有雷达读数的击球 | App 给出球速 ≥ 60% |
| 球速误差 | 两者都有的击球 | 有符号偏差单独报告；平均绝对误差 ≤ 15 km/h，P95 ≤ 25 km/h |
| 动作分类 | 单一动作段里 App 记的击球（段名即参考） | 大类一致（落地击球覆盖正反手）≥ 85% |
| 落点覆盖 | 有独立位置的触地 | App 给出位置 ≥ 50% |
| 落点误差 | 两者都有的触地 | 中位数 ≤ 0.75 m |
| 实时与采集 | 会话时长 | 看板「实时」≥ 99% 的时间；相机丢帧 ≤ 0.1%；分析落后 P95 ≤ 0.5 s |

## 出发前（在家）

- 两台设备装同一个版本（含 Phase 3：单拍片段与点对点直连）。
- 新版本第一次上真机时，先在家按 [界面打磨后的 15 分钟室内验收](device-validation.md#界面打磨后的-15-分钟室内验收2026-10-29-起未实测) 走一遍，界面或流程有问题先修好再去球场。
- 机位剩余存储 ≥ 预计时长 × 3.6 GB/小时，再留余量。看板的「机位状态」面板显示剩余空间。
- 看板配对页的「允许点对点直连」保持开启（默认开启）。
- 记下每位球员的持拍手。

## 到场布置

### 机位

- **位置**：底线后方，靠近中线，镜头朝球场、手机横放。画面要拍到整片球场：两条底线、边线、发球线和球网都清楚可见，双打外框的四个角都在画面内且不贴画面边缘，因为手动标定要点到这四个角。
- **高度**：仓库里还没有经过验证的最佳高度。先试几个可行的高度（三脚架升到最高、夹在围网上沿等），取能满足上面画面要求的一个。**记下实际高度、离底线的距离、偏离中线多少**，这是这次测试要产出的数据之一。
- **光线**：白天，避免镜头直对太阳。
- 倍率：开始记录前在机位上设好（点倍率、在倍率上拖动或双指缩放），拉近到双打四个外角刚好都在画面内，尽量不用橙色（数码放大）的倍率；记录中倍率锁定。把每次实测用的倍率记进记录表备注。
- 固定后尽量不要再碰机位：机位被碰后会丢掉旧球场、稳住后自动重新识别，这段时间不判界内外；改倍率也会让球场重新识别。
- **机位黑屏是正常的**：开始记录约 20 秒后，机位屏幕会自动变黑调暗（省电值守），采集和分析照常进行。轻点屏幕唤醒 15 秒，或在看板点「唤醒机位屏幕」。建议开启「引导式访问」，防止误退出 App。

### 看板

放在场边长椅附近，记下离机位的大致距离。

## 测试流程

### 0. 连接（最先做）

球场通常没有 Wi-Fi，所以点对点直连是这次的主要连接方式。

1. 两台设备都打开 Wi-Fi，但不连接任何网络；场地有 Wi-Fi 也先断开。看板显示二维码，机位扫码。
2. 记下扫码到连上用了多久，以及两端是否都显示「点对点直连」（看板在机位状态面板里，机位在连接状态里）。看板不在任何网络上时，配对码里没有地址，机位只用 Bonjour 查找，每次尝试有 3 秒等待宽限。
3. **1 分钟内连不上就改用热点**：一台手机开个人热点，另一台连上，看板刷新配对码，机位重新扫码。记下点对点失败时的现象，测试不要因此中断。
4. （可选）在看板配对页关掉「允许点对点直连」，机位重新扫码，确认没有共同网络时会明确连不上，而不是一直等待。确认后再打开，并重新扫码。

### 1. 球场与设置

1. 机位上「开始采集」，确认 1920×1080 / 60 fps、相机丢帧为 0。
2. 等机位自动识别球场，确认「识别状态」里「球场」显示「球场映射可用」。用实时画面上一个已知位置（例如中线与发球线的 T 点）目测核对球场线是否对齐。
3. 设置近端、远端持拍手。
4. 看「分析状态」里的「识别状态」：「球场」应为「球场映射可用」；打几拍后「击球」开始计数。记录中每段结束时看一眼「球速」「落点」的计数（例如「3 / 12 拍」）和主要原因，记在记录表的备注里。「人员」在降载 L1 时显示「已暂停」，这不影响击球分析。

### 2. 分段记录

看板「开始分析记录」。**每段开始时在看板（或机位）按一次「待复核」**。标记是事后切分各段的唯一依据，所以只在段开始时按，不在别处按。记录员在记录表上写下段名和开始时间。

每段球数事先定好（10–15 球），喂球或发球的人按数打完；检出按每段 App 拍数和计划球数比，不靠看录像补录。

| 段 | 内容 | 参考 |
| --- | --- | --- |
| 发球（近端） | 近端球员发 15 个球 | 雷达员站在发球者正后方，沿发球方向瞄准，记下每个读数，没测到写「—」 |
| 发球（远端） | 有第二位球员时，远端发 15 个 | 同上；雷达员换到远端 |
| 落点目标 | 慢速喂球或底线球，打向已量好坐标的标记 | 观察员记下每球落在哪个标记附近、偏多少（或用第二台手机拍） |
| 正手 | 底线正手 15 拍，只打正手 | 段名即动作参考；雷达可选 |
| 反手 | 底线反手 15 拍，只打反手 | 同上 |
| 截击 | 网前截击 10 个，只打截击 | 同上 |
| 高压 | 高压 5 个 | 同上 |
| 自由练习 | 正常练习，时间不限 | 用于检出统计；时间够长时顺便得到温升和耗电数据 |
| 双打（可选） | 有四个人时打一段正常双打 | 用于检出统计。App 不区分单打双打，用同一套分析；同一端两人持拍手不同时，把这一端设为「未知」 |

- 每段中途在看板「最近击球」里挑一拍，点「从机位取这一拍片段」，确认片段画面对得上那一拍，记下取片段时实时数据有没有卡顿。
- **不要挑样本**：App 记的每一拍都留在记录表里，包括擦网的、出界的。每段的球数按安排固定（例如喂 15 球），这样不用逐拍补录也能算检出。
- 单一动作段里只打这一种动作；混进别的动作时在现场记录表的备注里写下这一段，报告里把这段单列，不改段名。

### 3. 长时间运行（可选）

不单独安排。如果练习本身超过 1 小时，就自然得到温升、耗电和值守屏的数据：看板会把机位每秒的状态写进「机位状态记录」。结束时记下机位电量与温度。

### 4. 结束

1. 看板「结束」，记下结束时间、机位电量和温度。
2. 在机位上打开这次记录，「导出 › 诊断包（不含录像）」存到「文件」（iCloud 云盘也行）。诊断包里有机位每秒的球场识别、温度和负载，以及一页摘要；没有看板时也有。
3. 片段可以在球场取。**整段录像回家后在 Wi-Fi 下回传**（每小时约 3.6 GB），或用 Finder 的文件共享从机位拷出 `Zacks Court/Sessions` 文件夹，不要在球场用点对点回传。

## 参考值怎么记

### 球速

- 雷达单位设为 km/h。雷达员站在击球者正后方，沿出球方向瞄准；方向偏了读数会偏低（余弦误差）。
- 记录表写段名、第几球、读数，没测到写「—」。
- **口径不同**：雷达读的是出拍后的峰值速度；App 的球速是击球后前几个样本（跨度至少 0.25 秒）的飞行拟合，只算重力、不含空气阻力。预期 App 会偏低。报告里单独给出有符号偏差，不做任何修正。

### 落点

参考位置必须独立于 App：**不要用 App 自己识别的球场换算**，否则只测到了触地定位，没测到落点。

- **目标法**：用卷尺量出 4–6 个点并贴平面标记。坐标原点是近端左侧双打外角，x 向右（到对侧双打边线为 10.97 m），y 朝远端（到远端底线为 23.77 m）。观察员记下每球落在哪个标记、偏了多少。
- **第二机位**：第二台手机从侧面或远端拍，回家后用自研离线链（自动球场 + 球检测）自动求落点，不靠人看录像判断。这条参考依赖我们自己的模型，报告里要写明。

### 动作

- 不逐拍标注。参考就是段名：正手、反手、发球、截击、高压、喂球段里的每一拍都按这一类对照；「对拉」「自由练习」这类混合段不参与动作对照，只用于检出与稳定性。
- 段名要和上面的类别一致（可以加「近端」「远端」），生成记录表时脚本自动填 `ref_stroke`。
- 局限：段里 App 多记的非击球（捡球、拍球）也会按段名对照，所以误检会算成动作不一致；报告里同时看每段拍数和计划球数。

## 事后对照

1. 回传录像或拷出会话文件夹，找到看板上的 `Sessions/<会话ID>.json`（Mac 在 `~/Movies/Zacks Court/Sessions`）。机位上的副本是权威副本，两份的逐拍记录相同。
2. 生成记录表。每行是 App 记的一拍，带所在段、录像文件名和录像内的时间，方便定位：

   ```sh
   python3 scripts/field-test-sheet.py "$HOME/Movies/Zacks Court/Sessions/<会话ID>.json" --blocks "发球近端,发球远端,落点目标,正手,反手,截击,高压,自由练习" -o field-sheet.csv
   ```

   `--blocks` 按标记顺序给段名；数量和标记对不上时脚本会提示。机位断线期间补发的标记没有机位时间，脚本会按最近的事件估算并提示。单一动作段的 `ref_stroke` 由段名自动填好。
3. 只填仪器读数：`ref_speed_kph` 按段内顺序抄雷达读数，`ref_x_m`、`ref_y_m` 抄目标标记的坐标。段内 App 拍数和雷达读数个数对不上时，这一段不做逐拍球速对照，只报两边的分布，不看录像去对齐。不新增漏检行，不写「无」。
4. 出报告（每个数都带分母，缺失值不按 0 计）：

   ```sh
   python3 scripts/field-test-report.py field-sheet.csv --planned "发球近端=15,发球远端=15,正手=15,反手=15,截击=10,高压=5" --json field-report.json
   ```

5. 一并保留：诊断包（机位记录详情「导出 › 诊断包」）、看板上的机位状态记录（`<会话ID>-status.jsonl`，也在看板那边的诊断包里）、记录表照片、机位高度与位置、雷达型号、天气和光线。
6. 在 [验证记录](verification.md) 追加带日期的小节，写明样本量、门槛、结果，以及没测到什么。
